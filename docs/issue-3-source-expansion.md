# Issue #3 — 3차 수집처 확장 조사 및 검증

2026-11-01 KST. **진행 중이며 신규 수집처 배포 완료가 아니다.** 신규 수집 검증 전 main 병합 금지 조건을 유지한다. 기존 ALIO·나라일터 수집기, 활성화 설정, 운영 일정과 배포 워크플로는 변경하지 않는다.

## 운영 기준선과 중복 조사

공개 운영 피드 `https://ytbhana01-tech.github.io/midcareer-jobs/jobs.json`을 HTTP 200으로 읽고 1,178개 게시 레코드를 확인했다. 출처별 수집 개수는 ALIO 422건, 나라일터 757건이다. 중복 병합 전 개수와 게시 레코드 수는 다르다. 원래 수집 시각과 SHA-256은 [기준선 검증 결과](issue-3-baseline.json)에 기록했다. 신규 API 수집 결과가 아니라 기존 운영 피드 확인 결과다.

나라일터의 게시 레코드 중 기관명에 `교육청|교육지원청|학교`가 포함된 것은 166건, `부산광역시교육청`이 포함된 것은 14건이다. 이 수치는 기관명 문자열에 의한 사전 탐색이며 전국 교육청 전체를 포괄한다는 의미가 아니다. 부산교육청 학교인력채용 목록에 보이는 **2026학년도 광남초등학교 특수 시간강사 채용 3차 공고**는 나라일터 `307133`에도 같은 제목과 2026-11-04 마감으로 게시되어 있다. 제목만으로 자동 병합하지 않으며 실제 원문 ID 대조 전까지 중복 의심 사례로 취급한다.

새 후보 데이터의 고유 공고 수는 다음 도구로 고정된 기준선과 비교한다.

```sh
python -m scripts.audit_sources baseline.json --candidate candidate.json --output comparison.json
```

입력은 기존 정규화 피드와 같은 스키마다. 현행 병합 정책으로 출처 내부 중복, 기준선과 겹치는 공고, 추가 고유 공고, 실제 피드 순증감, 제외 개수와 새 공고 ID를 출력한다. 같은 제목만으로 병합하지 않는다. 비교는 출처별 독립적이며 여러 후보 출처의 추가 수를 단순 합산하면 안 된다. 이 도구는 이용 허락이나 실제 수집 성공을 인증하지 않는다. 추가 고유 수와 순증감은 기존 두 그룹을 잇는 공고가 있을 때 다를 수 있다.

## 구현과 검증

- `scripts/audit_sources.py`: 고정 운영 기준선과 신규 후보 비교. 네트워크와 운영 피드 변경 없이 재현 가능.
- `collect_all.py`: Actions 캐시가 없을 때 기존 다중 출처 피드의 primary 레코드를 출처별 원래 시각으로 복구. 기존 코드는 ALIO만 복구해 나라일터 장애와 캐시 유실이 겹치면 나라일터 데이터가 사라질 수 있었다. attribution만 있는 공고에는 전체 자격 증거가 없으므로 다른 출처 내용을 복사해 별도 공고를 만들지 않는다. 캐시가 있으면 캐시가 우선이다. 로컬에 없는 운영 피드를 자동 다운로드하는 기능은 추가하지 않았다.
- 단위 테스트 **63개 통과**. 캐시 유실+출처 장애 시 기존 ALIO/나라일터와 각 시각 보존, 원문 중복, 같은 제목의 다른 공고 보존, 마감 제외를 검증했다.
- 운영 피드 1,178건을 로컬에 일시 주입해 기존 브라우저 검증을 실행했다. 검색·출처 필터·상세·attribution·320/390/768/1440px·KST 마감·XSS·장애 상태 통과, 페이지 오류 0건. 작업 후 체크인된 jobs.json 원본을 복원했다.
- 운영 main의 신규 배포나 신규 수집 성공 Actions 실행은 아직 없다. PR CI 결과는 PR의 Checks에서 확인한다.

## 이어서 필요한 검증

현 클라우드 환경은 data.go.kr, apis.data.go.kr, 부산시, ALIO, 운영 Pages와 GitHub를 허용하지만 교육청·클린아이·나라일터 원문 도메인은 허용 목록에 없다. 환경 설정 적용을 요청했으며 우회하지 않는다. 이 세션에는 NARA_API_KEY가 주입되지 않았고 기존 Actions secret을 읽거나 다른 출처로 ALIO 키를 전달하지 않는다.

공식 채용 API/피드 확인 → robots와 개별 이용권리 확인 → 비밀정보 없는 응답 fixture → 독립 어댑터 → 실행 시간 상한·요청 간격·상세 캐시 → 기존 운영 기준선과 고유 수 비교 → 브랜치의 실제 수집 및 브라우저 검증 → 검증된 출처만 활성화·병합·Pages 배포 순서로 진행한다. 키 신청은 해당 API 계약과 필요성이 확인된 후에만 요청한다. 담당자 연락이나 이용 허락 신청은 사용자 지시 없이 보내지 않는다.
